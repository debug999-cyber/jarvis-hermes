# База знаний JARVIS (`jarvis-brain`)

> «Мозг» — это не логи и не чат-история. Это структурированная, самообновляющаяся база того,
> что JARVIS знает о вас и вашем мире, которую он **сам пополняет днём и сам пересматривает ночью**.

## Зачем, если у Hermes есть память

Встроенная память Hermes (`MEMORY.md` / `USER.md`) — это два текстовых блока, которые целиком
попадают в системный промпт. Это отлично для 20–40 строк «самого важного», но:

| | Память Hermes | jarvis-brain |
|---|---|---|
| Объём | ~2–3 КБ (весь текст в промпте) | тысячи заметок (в промпт попадают только релевантные) |
| Структура | свободный текст | типы, карточки, теги, связи, важность, уверенность, срок годности |
| Поиск | нет (всё и сразу) | FTS5 полнотекстовый + ранжирование |
| Исправления | перезапись строки | история изменений, архив, откат |
| Обслуживание | вручную | ночная ревизия агентом + автоуборка |

С 1.10 «оперативная» память Hermes дополнена его же провайдером **Holographic** (факты с поиском) — см. следующий раздел; таблица выше про MEMORY.md/USER.md.
| Эпизодическая память | нет (есть session_search по сырым логам) | дневник по дням, дистиллированный из диалогов |

Обе системы работают вместе: память Hermes — «оперативная» (самое главное всегда перед глазами),
brain — «долговременная» (всё остальное, по запросу и по релевантности).

## Два слоя с 1.10: факты — в памяти Hermes, структура — у JARVIS

С версии 1.10 включён официальный провайдер памяти Hermes **Holographic** (`memory.provider: holographic`):
локальный SQLite `~/.hermes/memory_store.db` с FTS5-поиском, trust-оценками и инструментами `fact_store` / `fact_feedback`.
Он сам подмешивает релевантные факты в каждый ход и виден из любого интерфейса Hermes (CLI, Desktop, панель, Telegram).

| Слой | Где | Что хранит | Кто пишет |
|---|---|---|---|
| **Факты** | `memory_store.db` (провайдер Hermes) | атомарные утверждения с trust | `brain_remember` (зеркало), авто-захват «запомни…», сама модель через `fact_store`, `hermes memory` |
| **Структура** | `brain.db` (`jarvis-brain`) | карточки с типами и связями, дневник дней, история изменений, журнал сбоев, индекс файлов ~/JARVIS | `brain_*`, `vault_*`, ночная ревизия |

Правила согласования (`plugins/jarvis-brain/facts.py`):
- каждая заметка `brain_remember` → факт (категория по типу: preference/habit → `user_pref`, project/decision/goal → `project`,
  howto/device → `tool`; теги `jarvis:<kind>,<карточка>,<теги>`; trust = уверенность заметки). Повтор не дублирует — `content` уникален;
- `brain_recall` возвращает поле `hermes_facts` — совпадения из памяти Hermes, которых нет среди заметок;
- контекст хода: факты подмешивает провайдер, JARVIS добавляет только карточки, дневник и файлы — без дублей;
- **перенос старых заметок**: `jarvis brain migrate` (install.sh запускает сам при обновлении). Идемпотентно, `brain.db` не трогает,
  архивные заметки не переносит. Проверка: `jarvis brain` → строка `hermes facts: N`, `jarvis doctor` → «Память Hermes (holographic)».

Панель Hermes (`hermes dashboard`, меню-бар → «Панель Hermes») получает вкладку **«База знаний»** — заметки, карточки, дневник, файлы
и факты в одном месте (`plugins/jarvis-brain/dashboard/`), плюс тему **JARVIS** (иконка палитры → JARVIS).

## Как это работает — один день из жизни

```
 09:00  Вы: «Джарвис, Анна теперь тимлид Atlas, пиши ей коротко»
        → модель вызывает brain_remember(kind=person, entity=Анна, tags=work)
        → HUD: 🧠 + #14 Анна — тимлид проекта Atlas, любит короткие письма
        (если бы модель забыла вызвать инструмент — фраза «запомни…» ловится авто-захватом)

 14:30  Вы: «набросай письмо Анне про перенос деплоя»
        → pre_llm_call ищет по тексту сообщения → в контекст попадает:
          [JARVIS memory] - #14 [person] (Анна) Анна — тимлид проекта Atlas, любит короткие письма…
                           - #10 [howto] (Atlas) Деплой Atlas делается командой make deploy…
        → JARVIS пишет коротко, упоминает правильную команду — без уточняющих вопросов

 18:00  Вы: «это уже не так, Анна ушла из Atlas»
        → brain_forget(id=14, new_content=…) — исправление с сохранением истории

 03:30  cron «ночная ревизия» (навык brain-nightly-review):
        1. maintain  — бэкап, точные дубли, просроченное, decay важности, VACUUM      (без LLM)
        2. digest    — журнал ходов за день → эпизод-резюме + новые устойчивые факты
        3. plan      — кандидаты: похожие заметки, конфликты, некатегоризированное,
                       пустые карточки, устаревшая таксономия                          (без LLM)
        4. решения   — модель читает план и формирует пакет операций                  (LLM)
        5. apply     — merge / archive / rekind / link / kind_rename / entity_merge…  (транзакция)
        6. export    — читаемый ~/.hermes/jarvis/BRAIN.md
        7. finish    — отчёт в таблицу reviews; в чат — [SILENT], если менять было нечего

 08:00  утренний брифинг видит вчерашний эпизод и актуальные карточки
```

## Модель данных

Файл: `~/.hermes/plugin-data/jarvis-brain/brain.db` (SQLite, WAL, FTS5). Смотреть можно чем угодно:
`jarvis brain sql "select * from notes limit 5"`, DB Browser for SQLite, Datasette.

```
kinds       таксономия типов знаний — агент может добавлять/переименовывать
entities    карточки: люди, проекты, места, устройства, организации, темы
notes       атомарные знания ── entity_id ─▶ entities
            поля: kind, tags, importance 1–5, confidence 0–1, source, status
                  (active|archived|merged|expired|superseded), superseded_by,
                  valid_from / valid_until (интервал, когда факт был верен),
                  access_count, last_accessed, created/updated
failures    журнал сбоев инструментов: tool, error_type, message, count, first/last_seen, resolved
relations   entity ──type──▶ entity  (works_at, part_of, leads, owns, friend_of…)
turns       сырой журнал ходов (обрезанный, 30 дней) → сырьё для дневника
episodes    дневник: один эпизод на день (summary + highlights)
changelog   каждое изменение: кто (agent|nightly|auto-capture|user), что, before/after
reviews     отчёты ночных ревизий + снимок статистики
notes_fts   FTS5-индекс (unicode61, префиксный поиск для русских окончаний)
meta        schema_version — миграции применяются автоматически при старте (сейчас v2)
```

Стартовая таксономия: `fact, preference, person, project, place, habit, decision, howto, goal, idea, event, device`.
Ночью агент может ввести новый тип (если в него попадёт ≥5 заметок) или слить редкие.

### Ранжирование при поиске
`score = bm25 + 0.4·importance + 0.5·confidence + 0.3·(обновлено за 30 дней)`.
В контекст хода попадают только заметки с `score ≥ min_score` (по умолчанию 1.2) — на «сколько
будет 2+2» контекст не подмешивается вовсе, промпт не раздувается.

### Дедупликация и конфликты при записи
Перед вставкой ищутся похожие активные заметки:
- сходство Жаккара **≥ 0.75** → существующая заметка обновляется (текст — более полный, importance — максимум,
  теги — объединение; старый текст возвращается в `previous`). «Кофе без сахара» и «кофе без сахара и молока» — одна запись;
- сходство **0.25–0.75 при том же типе или карточке** → новая заметка создаётся, но модель получает
  `possible_conflicts` с подсказкой архивировать устаревшую («живёт в Цюрихе» vs «живёт в Берне» — она сама
  спросит или решит по контексту, а не перезапишет молча). Что осталось — разберёт ночная ревизия.

### Редакция секретов
Токены (`ghp_…`, `sk-…`, `AKIA…`), длинные hex-строки, `пароль: …`, номера карт, приватные ключи заменяются на `[скрыто]`
**и в заметках, и в журнале ходов** ещё до записи на диск; заметка получает тег `redacted`, модель — предупреждение.

### Рефлексия (insights)
Ночью в плане приходит `reflection_material`: последние 7 эпизодов, решения/цели/привычки и уже существующие insights.
Модель может вывести 0–2 наблюдения-паттерна (`kind=insight`, confidence 0.6): «Дедлайны Atlas переносятся третью
неделю подряд — стоит заложить буфер». Это уровень выше фактов — то, что делает ассистента полезным, а не просто памятливым.

### Темпоральная память (что было верно раньше)
Идея из Graphiti/Zep: факт — не строка, а **интервал**. «Пользователь живёт в Цюрихе» получает `valid_from` при записи;
когда он переезжает, JARVIS делает `supersede`: старая заметка закрывается (`status=superseded`, `valid_until=сейчас`,
`superseded_by=id новой`), новая создаётся с той же карточкой. Поиск видит только новую, а `brain_history` / `/brain history`
отвечают на «где я жил до Берна?» с датами. `brain_forget(new_content)` остаётся для *ошибок* — там прошлое значение не важно.

### Авто-привязка к карточкам
При записи без `entity` заметка сама привязывается к карточке, чьё имя встречается в тексте (учитываются русские
словоформы: «бюджет Атласа» → карточка «Атлас»). Мем0-стиль entity linking без отдельного вызова модели.

### Ментальные модели (живые резюме карточек)
Идея из Hindsight: у каждой сущности есть `summary` — не архив фактов, а «что это сейчас». Ночью план содержит
`stale_entity_summaries` — карточки с ≥3 заметками, где заметки новее резюме; агент перечитывает их и переписывает
резюме операцией `entity_summary`. Именно оно уходит в справку перед встречей и в `brain_reflect`.

### Журнал сбоев (самодиагностика)
Хук `post_tool_call` пишет каждый неуспешный вызов инструмента в `failures` (одинаковые сбои схлопываются в счётчик).
Ночью повторяющиеся сбои превращаются в `howto`/`insight` («mac_calendar падает без прав Автоматизации — предложить
`jarvis selftest --fix`») и помечаются `resolve_failure`; не встречавшиеся 30 дней — закрываются сами. Открытые сбои
видны на HUD (K) и в `/brain failures`.

### Reflect — «что ты знаешь о X»
`brain_reflect(question)` — один вызов вместо серии recall: заметки, карточки с резюме, эпизоды дневника и история
изменений. Модель синтезирует связный ответ («сейчас так, месяц назад было иначе, важно помнить…»). Аналог операции
`reflect` в Hindsight, но синтез делает основная модель — лишнего вызова LLM нет.

### Верификация сомнительного
Утром `brain_review verify` выдаёт 1–2 факта с `confidence < 0.6` и `importance ≥ 3` (старше суток), JARVIS уточняет их
одной фразой в конце брифинга и ставит тег `verify_asked`, чтобы не спрашивать дважды.

### Голос: словарь и «полировка»
- `pre_transcription`: имена людей/проектов из базы (`vocabulary()`) подмешиваются в `initial_prompt` Whisper —
  «Атлас», «Анна», «Acme» перестают распознаваться как шум.
- `transform_llm_output`: на голосовых платформах финальный ответ очищается от markdown и ужимается до 4 предложений
  («Подробности — в текстовом ответе»). Отключается `voice_polish: false`.

## Инструменты (что видит модель)

| Инструмент | Назначение |
|---|---|
| `brain_remember(content, kind, entity, tags, importance, confidence, valid_until)` | сохранить знание |
| `brain_recall(query, kinds, entity, limit, scope=notes\|episodes\|all)` | целевой поиск по знаниям и/или дневнику |
| `brain_forget(id \| query, new_content, reason)` | исправить или архивировать |
| `brain_entity(get \| upsert \| list \| relate)` | карточки и связи |
| `brain_review(stats \| maintain \| plan \| apply \| digest_queue \| save_episode \| finish \| export \| profile \| episodes \| changelog \| failures \| verify \| restore)` | обслуживание и реструктуризация |
| `brain_reflect(question)` | всё по вопросу одним вызовом: заметки + карточки + эпизоды + история |
| `brain_history(history \| supersede)` | что было верно раньше; темпоральная замена факта |

Операции `apply` (пакет в одной транзакции): `merge, archive, update, supersede, entity_summary, resolve_failure,
rekind, retag, link, kind_define, kind_rename, entity_merge, entity_update, relate`. Физического `DELETE` заметок нет.

## Настройки (`plugins.entries.jarvis-brain.settings`)

```yaml
inject_context: true     # подмешивать релевантные знания в каждый ход
context_limit: 5         # максимум заметок в контексте
min_score: 1.2           # порог релевантности (выше — строже)
log_turns: true          # журнал ходов для дневника (обрезка 700 символов/сообщение, 30 дней)
auto_capture: true       # страховка для «запомни …»
export_path: ~/.hermes/jarvis/BRAIN.md
backup_mirror: ""        # напр. ~/Library/Mobile Documents/com~apple~CloudDocs/JARVIS — копия последнего бэкапа в iCloud
log_failures: true       # журнал сбоев инструментов
stt_vocabulary: true     # имена из базы → подсказка Whisper
voice_polish: true       # голосовой ответ без markdown, ≤4 предложений
```

## Безопасность и приватность

- База — локальный файл, никуда не синхронизируется. Бэкапы рядом (`brain.bak-*.db`, хранится 7).
  Если задать `backup_mirror` в iCloud Drive — копия `brain.latest.db` попадёт в облако Apple (удобно при потере Mac,
  но это уже не «только локально»; секреты в базе всё равно редактируются).
- Секреты в базу не пишутся (закреплено в SOUL.md и навыке; ночная ревизия архивирует найденное с reason=secret).
- Журнал ходов обрезан и удаляется через 30 дней после переваривания; отключается `log_turns: false`.
- Полный аудит в `changelog`: любое ночное изменение можно увидеть (`jarvis brain log`) и откатить вручную из `before`.
- Ночная ревизия — единственный процесс, который меняет структуру; работает по явным правилам навыка
  («сомневаешься — не трогай», importance 5 неприкосновенна).

## Откат ночной ревизии

```bash
/brain restore                 # в чате — из последнего бэкапа (текущая база сохраняется как .pre-restore-*)
jarvis brain restore           # в терминале — с выбором файла и подтверждением
```
Бэкап делается автоматически в начале каждой ревизии (`maintain`), хранится 7 последних.

## Идеи для развития

- Векторный поиск поверх FTS (sqlite-vec + локальные эмбеддинги) для семантических совпадений без общих слов
  (миграции `Brain._migrate` уже есть — это будет schema v3).
- Импорт Obsidian / закладок (контакты и календарь уже импортируются `jarvis brain import`).
- Кросс-энкодерное переранжирование результатов (как в Hindsight), когда база перевалит за несколько тысяч заметок.
- Панель «граф знаний» на HUD (сущности и связи).
